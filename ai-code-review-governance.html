为什么

传统 PR Review 的三个结构性缺陷

01

稀缺性

资深 reviewer 是瓶颈。PR 数量随团队规模线性增长，但审查能力不同步扩张——排队是必然，质量是偶然。

02

重复性

大量 review 时间消耗在机械扫描——空指针、日志脱敏、测试缺失、依赖升级风险。高价值人力被低价值工作占据。

03

不一致性

不同 reviewer 关注点差异导致审查质量波动。相同问题在不同 PR 里命运不同，标准无法统一。

⚡ 剪刀差正在扩大： AI 提高了代码产出速度，却没有同步提升 review 吞吐——这个差距会越来越大。

02 / 15
真实价值

AI Review 不是"更快看完代码"

🔍

审查前移

在人工 reviewer 进入前，过滤掉 60~70% 的基础问题。提交质量门槛从人工判断前移到代码写完时。

🎯

注意力聚焦

让人工 reviewer 把时间花在 业务逻辑、架构判断和系统边界 上，而不是扫描机械错误。

🛡️

覆盖兜底

跨文件影响、依赖链分析 等人工容易漏掉的维度，由 AI 系统性覆盖，不依赖 reviewer 的记忆力。

目标： AI 做掉 70% 的基础扫描，人把主要精力放在最值钱的 30% 判断上。 这不是"替代"，而是重新定义人机分工。

AI Review 质量上限 = 指令质量

全局
级

影响所有 AI 操作，不只是 review。代表文件：CLAUDE.md / AGENTS.md。约定整体行为准则和基础安全规则。

仓库
级

REVIEW.md — 仓库级规则

只影响当前仓库。结构建议：Always check · Style · Skip。每周 1~2h 由 instruction owner 维护。

路径
级

Path Instructions — 细粒度差异化

针对特定目录定制规则。src/api/** 严格检查认证  ·  src/payment/** 重点检查并发安全  ·  src/gen/** 跳过自动生成文件。

实践建议： 为每个仓库指定 review instruction owner，每周花 1~2 小时维护规则——规则腐烂速度往往快于维护速度，必须制度化保障。

06 / 15
阶段 01

开发过程分层 Review — 四大核心原则

Review 前移

设计阶段发现问题的修复成本，远低于代码阶段。Spec 漏一个约束，到实现才发现，返工成本放大 10 倍。

分层 Review

不同阶段暴露不同类型风险。Spec Review → Plan Review → Spec Compliance Review → Code Quality Review，四道独立质量门。

证据驱动

feels correct → proven correct。Review 必须基于可验证证据：测试通过、git history、smoke check。

Gate 化

Review 必须具备阻断能力。模糊建议会被忽略——必须是明确的 PASS / FAIL gate。

子代理隔离原则： reviewer subagent 不继承主会话历史，避免"上下文污染"。 Review 建议是 suggestions，不是命令——先验证是否成立，再决定采纳或 push back。

阶段 02

本地 Agent Review — Push 前的第一道防线

/review
通用代码审查
  • gh pr list → 查看待审 PR
  • gh pr view / diff → 获取详情和 diff
  • 输出：概述 + 代码质量 + 改进建议 + 风险点
  • 审查：正确性 · 项目约定 · 性能影响 · 测试覆盖 · 安全
/security-review
专项安全审查
  • 只报 ≥ 0.8 置信度的明确可利用问题
  • 17+ 类硬性排除规则（DoS · 速率限制 · 测试文件）
  • 子任务并行探索 → 误报过滤 → 置信度阈值
  • 重点：输入校验 · 鉴权 · 加密 · 注入 · PII 泄漏

核心价值： 在 push 前就消灭基础安全漏洞——修复成本最低的时间点。 单模型输出 + 严格误报控制 = 高信噪比。

人机协作

边界划分 — AI 做什么，人做什么

🤖 AI 负责

  • 第一轮全量扫描
  • 基础安全 / 测试 / 文档问题
  • 风险点预标注
  • 低复杂度修复建议
  • 评论聚合与 briefing

PR 打开时：生成摘要 + 高风险区域标注
人工进入前：生成 briefing（改了什么 / 最值得看哪里）
Review 收尾：汇总 comment + closing checklist

👤 人工负责

  • 业务逻辑正确性判断
  • 架构合理性判断
  • 系统边界和回滚策略
  • 最终 merge 责任
核心判断力不能外包

AI 不理解域模型，无法判断折扣计算对特定定价规则是否正确；无法评估 PR 整体设计方向是否符合系统目标。

Benchmark — 如何衡量 AI Review 质量

北极星指标 说明 定位
用户接受率 review comment 被开发者采纳的比例 最直接价值信号
信噪比 (SNR) 有效 comment / 总 comment 衡量噪声水平
可读性 comment 是否表达清晰、定位准确 —
详细程度 问题描述、复现场景、修复建议是否完整 —
p95 延迟 review 完成时间的长尾分布 工程 SLA
成本 每次 review 的 token 消耗和费用 可持续性

企业内部 Benchmark 建议： 收集历史高质量 PR (golden comments) → 持续跟踪 AI comment 与开发者后续修复的对齐率 → 定期抽样做人工 precision/recall 评估 → 建立 regression 测试集防止质量下降。

研讨议题

关键问题

1
规则该限定到多细致？ AI review 实测只能发现约 40% 的真实问题。规则过于细致，则漏报多，如果过于宽泛则又会导致噪声淹没信号。团队对这两种错误的容忍度各是多少？
2
Review的维度有哪些？ 如何区分Review和开发的界限，review成本和收益如何平衡？
3
本地和云端如何分工？ 本地通过AI Agent触发skill检视和远端sophia根据MR自动触发的审计责任边界是什么？
4
规则文件如何避免变成"墓地"？ AGENTS.md或REVIEW.md 写了很多规则，但规则腐烂速度往往快于维护速度。instruction owner 机制如何保证不流于形式？
5
人于AI分工的边界在哪，资深 reviewer 省下来的时间去哪了？ AI 做掉 70% 基础扫描后，资深工程师会真的转向架构或逻辑判断，还是被更多 PR 填满？
